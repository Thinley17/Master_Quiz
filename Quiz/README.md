# QuizMaster — Django Online Quiz App

A Django app for creating, taking, and tracking quizzes. Staff users can
create quizzes/questions; any logged-in user can take quizzes and see their
results on a personal dashboard.

## Roles and quiz workflow

- **Students** register through the public site. They can browse active quizzes by subject, attempt quizzes during their availability window, and review their own results.
- **Teachers** are Django staff accounts. Enable a teacher in `/admin/` (or create one with `createsuperuser`); they can create and manage only their own quizzes, questions, and Excel imports.
- Each quiz has a subject, active/inactive status, optional start and end date/time, and a maximum attempt count. Availability is enforced when a student submits, not just when the page is displayed.
- Teachers can import a batch from the question screen. Download the supplied Excel template there and use the columns `question`, `choice1`–`choice4`, and `correct_answer` (choice number or exact text).

## Quick start (localhost)

```bash
# 1. Create and activate a virtual environment
python -m venv venv
# Windows:
venv\Scripts\activate
# macOS/Linux:
source venv/bin/activate

# 2. Install dependencies
pip install -r requirements.txt

# 3. Apply database migrations (uses SQLite out of the box, zero setup)
python manage.py migrate

# 4. Create an admin account (this account can create quizzes)
python manage.py createsuperuser

# 5. Run the dev server
python manage.py runserver
```

Then open http://127.0.0.1:8000/ in your browser.

- Log in with your superuser account to create quizzes (via the "Create
  Quiz" button, or via /admin/).
- Any registered user (Register link on the home page) can take quizzes
  and view their dashboard.

## Brevo transactional email

New student accounts are created only after the email verification code is
confirmed. OTP messages, password-reset messages, and other Django email are
sent through Brevo's transactional email HTTPS API; the app does not use SMTP.
Add these settings to `Quiz/.env` using an API key and sender address from your
Brevo account:

```dotenv
BREVO_API_KEY=your_brevo_api_key
BREVO_SENDER_EMAIL=verified-sender@example.com
BREVO_SENDER_NAME=QuizMaster
BREVO_API_TIMEOUT=20
```

The sender address must be verified in Brevo. Keep `.env` private and never
commit or share the API key. The same configured sender is used for OTP and
password-reset email.

The code is sent to the email address entered on the registration form and
expires after 10 minutes. Each account has its own password; using the same
password for accounts with different email addresses is allowed.

## Security configuration

Passwords are stored as one-way hashes. With the `bcrypt` dependency installed,
new passwords use Django's bcrypt-SHA256 hasher and existing PBKDF2 passwords
are upgraded after successful login. New passwords must be at least 8 characters
and include a symbol such as `!`, `@`, or `#`.
Login attempts are throttled after five failures per account/IP pair; OTP codes
allow five guesses. Registration email is rate limited. The local fallback
throttle uses in-process memory; configure Redis for a multi-process deployment.

Django's ORM parameterizes database queries, templates auto-escape user content,
and teacher actions are restricted to quizzes owned by that teacher. Session
IDs are generated by Django's cryptographic random session store, rotate at
login, expire after one hour, and are cleared on logout. Cookies use HttpOnly
and SameSite=Lax; Secure cookies and HTTPS redirects are enabled when DEBUG is
off. Admin sign-ins use the same login portal as student and teacher sign-ins,
then return to `/admin/` when the account has admin access. A random local
secret is stored in the ignored `.local_secret_key` file.

For production, set these environment variables before starting the app (use a
real HTTPS domain and a newly generated secret; never commit the values):

```powershell
$env:DJANGO_DEBUG = "False"
$env:DJANGO_SECRET_KEY = "<generate a private random value>"
$env:DJANGO_ALLOWED_HOSTS = "quiz.example.org"
$env:DJANGO_CSRF_TRUSTED_ORIGINS = "https://quiz.example.org"
$env:DJANGO_SECURE_SSL_REDIRECT = "True"
$env:DJANGO_DB_SSLMODE = "require"
$env:DJANGO_CACHE_URL = "rediss://<private-redis-host>:6379/1"
$env:DJANGO_DATABASE_URL = "postgresql://<user>:<password>@<private-db-host>:5432/<database>"
python manage.py check --deploy
```

If HTTPS terminates at a reverse proxy, set `DJANGO_TRUSTED_SSL_PROXY=True` only
when that proxy overwrites `X-Forwarded-Proto`. Production needs HTTPS end to
end, a shared private Redis service for rate limits, and secrets supplied by the
hosting environment. Django does not encrypt the local SQLite file itself: keep
the database and backups on encrypted storage (or use a managed database with
encryption at rest and TLS). Production PostgreSQL connections use TLS with
`sslmode=require` by default. Providers with a publicly trusted database
certificate can use `DJANGO_DB_SSLMODE=verify-full`; supply a CA bundle with
`DJANGO_DATABASE_SSLROOTCERT` when needed. Render's internal PostgreSQL URL
supports `sslmode=require` for encrypted private-network connections. Enable
the provider's encryption-at-rest and encrypted-backup options.
The app limits access to student results by owner and teacher role, but storage
encryption must be provided by the host/database.

## PostgreSQL setup (optional for local development)

Local development uses SQLite. To use PostgreSQL locally, install the listed
dependencies and set `DJANGO_DATABASE_URL` before running migrations. For
example, create the database and role in `psql`:
```sql
CREATE DATABASE quiz_db;
CREATE USER quiz_user WITH PASSWORD 'your_password';
GRANT ALL PRIVILEGES ON DATABASE quiz_db TO quiz_user;
```

Then set the connection string in PowerShell:

```powershell
$env:DJANGO_DATABASE_URL = "postgresql://quiz_user:<password>@localhost:5432/quiz_db"
python manage.py migrate
```

## Bugs found and fixed in this pass

The project as uploaded would not run. Here's everything that was wrong
and what was changed:

1. **`quiz` app was never registered.** `manage.py` uses
   `online_quiz.settings`, but that settings file's `INSTALLED_APPS` was
   missing `'quiz'` — meaning no migrations, admin, or app functionality
   could ever work. (There was a second, unused `online_quiz_project/`
   folder with a partial fix — Postgres config, `quiz` added — that was
   never wired up. It's been removed to avoid confusion; the fix was
   folded into the real settings file, `online_quiz/settings.py`.)

2. **Missing auth redirect settings.** Added `LOGIN_URL`,
   `LOGIN_REDIRECT_URL`, and `LOGOUT_REDIRECT_URL` — without these,
   Django redirects after login/logout to `/accounts/profile/`, which
   doesn't exist and 404s.

3. **Template filename typo:** `quiz_list.html` was saved as
   `quiz.list.html`, so the quiz list view couldn't find its template.
   Renamed.

4. **`take_quiz.html` had the wrong content** — it was an accidental
   copy-paste of the "delete question" confirmation page. Taking a quiz
   never actually worked. Rewritten to render the quiz's questions as
   radio-button choices and submit answers.

5. **`quiz_form.html` had the wrong content** — it was a copy of the quiz
   *list* page instead of a create/edit form. Rewritten to render the
   actual form fields.

6. **Broken URL reference:** templates used `{% url 'register' %}`, but
   the `register` view is namespaced under `quiz:` (`app_name = 'quiz'`
   in `quiz/urls.py`). This threw `NoReverseMatch` on every page that
   rendered the nav bar while logged out. Fixed to `{% url 'quiz:register' %}`
   in `base.html`, `home.html`, and `registration/login.html`.

7. **No migrations existed** for the `quiz` app (only the migrations
   package's `__init__.py` was present). Generated
   `0001_initial.py` and applied it.

8. **`admin.py`** had `inlines` set on a `TabularInline`, which Django
   doesn't support (nested inlines aren't a thing) — it was silently a
   no-op, and `Question`/`Choice` had no way to be managed from
   `/admin/`. Registered `Question` in the admin with `ChoiceInline` so
   quiz content can be fully managed from the Django admin as well as
   the app's own forms.

9. **Missing `STATICFILES_DIRS`**, added pointing at `quiz/static`.

## Verified working

The full flow was tested end-to-end against a running dev server:
registration/login/logout, staff-only quiz creation, adding a question
with 4 choices, taking the quiz as a regular user, scoring, the results
page, and the personal dashboard — all confirmed working, along with
permission checks (non-staff users get a 403 on quiz-creation routes).
